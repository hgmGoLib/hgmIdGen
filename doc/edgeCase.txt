设计须知与极限情况
==================
本文件集中记录 hgmIdGen 的设计前提和各种极限/边界情况.
这些是选型和排错时最容易踩坑的点, 请在依赖某个"看起来成立"的性质前先读这里.
配合 implDetail.txt (二进制布局) 一起看.


1. 递增计数器溢出 (每毫秒最多 2^30 个不碰撞递增)
===============================================
* 递增段最多承载 30 bit, 最大值 2^30-1 = 1073741823.
* nextId 返回的是 uint32, 会一直 +1, 但 encodeVarLenUint32 里有一步 val &= 0x3FFFFFFF, 只保留低 30 位.
* 极限情况: 同一毫秒内在同一进程调用超过 2^30 次时, 计数器高 2 位被掩掉, 递增值回绕.
    * 这会让递增段不再唯一, 碰撞概率上升 (此时只能靠随机段兜底).
* 现实评估: 同一毫秒 10 亿次调用几乎不可能达到, 正常业务不用担心.
    * 但如果你在 benchmark / 压测里紧凑循环生成 id 且不推进时间, 有理论上撞到这个上限的可能.


2. 变长递增会挤占随机段长度 (熵随负载下降)
=========================================
* 随机段长度 = 总长度 - 6 - 递增段长度.
* 递增值越大, 递增段越长 (1->4 字节), 随机段就越短:
    * NewId 随机段 11 字节(递增小) ~ 8 字节(递增到 30 bit).
    * NewSecureId 随机段 19 字节 ~ 16 字节.
* 极限情况: 同一毫秒内高频生成时, 后面的 id 随机段更短, 单纯看随机段的抗碰撞能力会略降.
    * 但此时递增段本身是唯一的(见第 1 条), 两方面合起来仍然极难碰撞.
* 结论: 抗碰撞是"递增唯一性 + 随机" 双保险, 不要只盯着随机段长度算概率.


3. 时钟回拨 / 时间不单调 (递增和排序的前提)
=========================================
* "同进程大概率递增" 和 "字符串排序==时间排序" 都建立在系统时钟单调递增的前提上.
* nextId 的重置条件是 lastT != t (时间"不同"就把计数器归 0), 不是"变大"才归 0.
* 极限情况 - 时钟回拨:
    * 如果 NTP/手动改时间让时钟回退到一个较早的毫秒 t, 该毫秒的计数器会从 0 重新开始.
    * 这段时间生成的 id 时间段会比之前的小, 破坏"递增"和"排序"性质.
    * 同一个被回拨命中的毫秒里, 递增值可能和之前重复, 此时是否碰撞完全靠随机段区分
      (随机段不同 -> 极大概率仍不碰撞, 但顺序性已经没有保证).
* 结论: 需要严格全局单调的场景, 不要假设本库能对抗时钟回拨.


4. 排序保证及其前提
==================
* 因为: 时间段大端在最前 + 递增段变长编码的高 2 位随数值单调 + base32 字符表按 ascii 递增,
  所以 id 的字符串字典序 == 其二进制字节序 == (时间, 递增) 的大小序.
* 前提与边界:
    * 只在"同一进程 + 时钟单调"下成立 (见第 3 条).
    * 跨进程之间只保证按时间大致有序, 同一毫秒内不同进程之间没有全局递增关系.
    * 同一(毫秒,递增值)不会出现两个真实 id (递增值每次调用都不同), 所以随机段不影响两个真实 id 的相对顺序.


5. Min*AtTime 只能当"下界"用
============================
* MinIdAtTime / MinSecureIdAtTime 生成的是: 6 字节时间 + 递增段和随机段全 0, 再 base32.
* 因为排序保证(第 4 条), 它是该毫秒所有真实 id 的严格下界.
* 正确用法: where id >= MinIdAtTime(t0) and id < MinIdAtTime(t1) 做时间范围扫描.
* 注意: 它不是一个"真实生成过"的 id, 只是一个排序用的边界值; 不要把它当作有效业务 id 存库.


6. 全进程共享同一个递增计数器
============================
* NewId / NewSecureId / NewIdBinary 都调用同一个 nextId, 共享同一个全局
  gNewIncRandIdCtx (同一把锁 + 同一个计数器 + 同一个 lastT).
* 影响:
    * 三种 id 混合调用时, 递增计数器是全局连续的, 而不是每种各自一份.
    * 好处: 混调也不会因为各自计数导致同毫秒内递增值撞车.
    * 代价: 高并发下这把全局锁是唯一的串行点 (随机段的取用也在另一把锁里串行).


7. randFast 随机源的性质
========================
* 随机数来自 crypto/rand, 但经过 zlib_hgmRandFast.go 的 512 字节缓存批量取用.
* 批量缓存只是"少调用几次 rand.Read", 取出的字节仍然是 crypto/rand 产出的, 熵不因缓存降低.
* 源码注释里写了 "安全性未知", 指的是这种批量封装本身未做正式安全审计, 而非随机源被削弱.
* MustReadWithLock 内部挂锁, 保证多 goroutine 并发取随机数据安全.


8. 时间上限
==========
* 时间段 48 bit 毫秒, 约可表示 8925 年 (从 1970 起), 到约公元 10895 年.
* 超过后高位溢出被截断, 但这远超任何现实需求, 仅作为理论边界记录.


9. 校验函数只做格式校验
======================
* IsValidId / IsValidSecureId 只校验: 长度对不对 + 字符是否都在 base32 表内.
* 它们不解码、不校验时间是否合理、不校验递增段结构, 也不能证明这个 id 一定是本库生成的.
* IdToIdBinary 比 IsValid 多一步: 长度对 + 字符合法 + 能成功 base32 解码到 18 字节.
