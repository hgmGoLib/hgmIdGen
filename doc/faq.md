# FAQ — 设计取舍说明

本文说明 hgmIdGen 在时间精度、counter、校验语义、命名、格式稳定性等方面的设计取舍和边界.
配套细节见 [`implDetail.md`](implDetail.md)(二进制布局)与 [`edgeCase.md`](edgeCase.md)(极限情况).

---

## 一、NewSecureId 的时间精度与 counter

### NewSecureId 为什么用毫秒级时间,而不是秒级/分钟级时间桶?

安全性来自随机段,不来自时间段.NewSecureId 的随机段有 16\~19 字节(128\~152 bit),这是"猜不到未使用 token"的来源;时间从来不是秘密,把时间桶变粗不增加任何安全性.

毫秒时间提供两个功能:字符串可按时间排序、`MinSecureIdAtTime()` 可作时间范围扫描下界.粗时间桶会牺牲这两点,却换不到安全收益,因此采用毫秒级.结构上也与 NewId 保持一致.

### NewSecureId 为什么暴露同毫秒内的 counter?

counter 提供同一毫秒内的确定性去重.只靠随机段去重是概率性的;有了 counter,同进程同毫秒内每个 id 的递增段天然唯一,碰撞只可能落在随机段,形成双保险.

counter 会暴露 qps 这一侧信道的信息量很小:时间精度为 1 毫秒,从 counter 至多能推算"某毫秒内本进程生成了几个 id",无法得到一秒内的分布,也无法得到跨进程的总量.以极小的 qps 侧信道换取同毫秒确定性去重.

需要完全消除时间/counter 信息的场景,应改用不排序的纯随机 token(见"纯随机 token"一节),而不是削弱 NewSecureId.

### NewSecureId 的定位:可排序安全 token,还是更长的普通 ID?

定位是**带时间前缀、可排序的安全 token**.

* 结构与 NewId 相同(时间 + 递增 + 随机),区别仅在随机段更长.
* "安全"指攻击者无法猜出一个合法且尚未分配的 token(随机段 128+ bit 兜底),适合 sessionId / accessToken.
* 不保证零信息泄露:时间段可反解(设计特性),counter 可推算.威胁模型要求 token 不含任何可推断信息时,应使用纯随机 token.

## 二、IsValidId / ParseTimeFromId 的语义

### IsValidId 校验的是"格式合法"还是"规范编码合法"?

只校验格式:长度为 29,且每个字符都在 base32 字符表内.

这是一道廉价的语法门:不解码、不校验时间是否合理、不校验递增段结构,也不能证明字符串一定由本库生成或为 canonical 编码.需要更强保证时用 `IdToIdBinary()`,它会真正 base32 解码到 18 字节,长度或字符非法时返回 error.

### IsValidId 为什么不 decode 再检查 canonical?

IsValidId 定位是廉价语法门,canonical 归一化由 `IdToIdBinary()` 负责.这里存在一个需要注意的边界(实测确认):

* 29 字符承载 145 bit,而二进制只有 144 bit,末字符有 1 个 trailing bit 冗余.
* Go 的 `encoding/base32` 解码器不校验该 trailing bit.实测 `"…1"` 与 `"…2"` 两个不同字符串会解码成同一个 18 字节二进制.
* 因此一个非 canonical 变体字符串能通过 IsValidId,并 decode 出与 canonical 串相同的 binary.

使用准则:

* 只存/比较本库自己产出的字符串(都是 canonical)时,一一对应成立.
* 可能接收外部构造的字符串且直接以字符串做主键/比较时,先用 `IdToIdBinary()` 归一到二进制再比较/存储,或自行加 canonical 校验.

### ParseTimeFromId 遇到非法输入为什么返回零值而不是 error?

失败时返回 `time.Time{}` 零值,不返回 error.

* 全库时间解析函数统一采用"零值即失败"的哨兵约定(`ParseTimeFromId` / `ParseTimeFromSecureId` 一致),调用方用 `t.IsZero()` 判断即可.
* 需要严格拒绝外部输入时,先 `IsValidId()` 过一道再解析,校验与解析职责分离.

## 三、counter 与变长编码

### counter 变长编码的主要目的:省长度、增加随机位,还是排序?

主要目的是在固定总长度下,让常见情况(counter 较小)拿到尽可能长的随机段,即"省长度 → 把省下的字节让给随机".

* 总长度固定(NewId 18 字节).counter 若固定 4 字节,随机段永远只有 8 字节;变长后 counter 绝大多数时候只占 1 字节,随机段有 11 字节,常见情况多 3 字节熵.
* 排序是顺带保住的性质:变长前缀高 2 位随数值单调递增,变长不破坏排序(见 [`edgeCase.md`](edgeCase.md) 第 4 条),但这是约束,不是动机.

优先级:增加常见情况随机位 > 固定总长度 > (顺带)不破坏排序.

### counter 溢出后同毫秒内的顺序如何?

同一进程同一毫秒内调用超过 `2^30`(约 10.7 亿)次时,递增段高 2 位被掩码回绕,**此毫秒内不再保证递增顺序,也不再保证递增段唯一**,只能靠随机段兜底防碰撞.

现实中同毫秒 10 亿次基本不可能达到,压测紧凑循环、不推进时间时有理论可能.详见 [`edgeCase.md`](edgeCase.md) 第 1 条.

### 时间回拨如何处理?

本库时间取自 `time.Now()`(wall clock),**不保证强单调**.NTP/手动改时间导致时钟回拨时,"递增"和"字符串排序 == 时间排序"两条性质都会被破坏;被回拨命中的毫秒里递增值可能与之前重复,是否碰撞完全交给随机段.

需要严格全局单调的场景,不要假设本库能对抗时钟回拨.详见 [`edgeCase.md`](edgeCase.md) 第 3 条.

## 四、随机源与并发

### randFast 用于 NewSecureId 是否削弱安全性?

不削弱.randFast 的字节全部来自 `crypto/rand`,一次读 512 字节缓存后每个字节只被消费一次顺序取出,不复用随机字节,熵不因缓存下降,仅减少 `rand.Read` 调用次数,功能上等价于每次直接 `crypto/rand.Read`.

源码注释里的"安全性未知"指这层批量封装本身未做过正式安全审计,不是随机源被换弱.

### 全局 mutex 的目标吞吐是多少?

当前未设定量化吞吐目标,也未提供并发 benchmark.

* 有两把锁,临界区都极小:`nextId` 的计数器锁、`randFast` 的取随机锁.
* 设计定位是普通应用生成主键/token 的速率,离锁竞争瓶颈很远.
* 若实测某条热路径卡在全局锁上,可再考虑 per-P 分片计数器 / 分片随机池.

## 五、命名、稳定性、唯一性、纯随机 token

### 为什么不提供 Go 风格别名 NewID / NewSecureID / IDToBinary?

命名采用逐词拼接、每个单词都能一眼读出的驼峰法:首字母大写,字段名/类型名/JSON 名全程 ascii 一致,不做大小写缩写转换.`ID` 这种全大写缩写不像一个独立的词,可读性更差,因此维持 `NewId` / `NewSecureId` / `IdToIdBinary`,不加 Go 惯例的全大写别名.

### ID 格式是否长期稳定,能否作为数据库长期存储格式?

格式稳定,可长期存库.三个格式是稳定契约:

* NewId → 29 字符 / 18 字节二进制
* NewSecureId → 42 字符 / 26 字节二进制
* 二进制三段式布局 + base32 字符表固定不变

存字符串(canonical)或存 18/26 字节二进制均可.二进制更省空间,字符串更直观且可直接排序.

### 自定义 base32 是否保证任意合法字符串只有唯一 binary 对应?

不保证反向唯一(实测确认):

* 正向(binary → 字符串)确定且唯一,本库产出的都是 canonical 串.
* 反向(字符串 → binary)不是一一对应:末字符有 1 个冗余 trailing bit,`"…1"` 与 `"…2"` 会解码成同一个 binary(见 IsValidId 一节).
* 使用准则:只用本库产出的字符串时一一对应成立;接收外部构造的字符串时,先 `IdToIdBinary()` 归一到二进制再比较/存储.

### 是否提供纯随机 token API?

不提供.纯随机 token 直接调用系统库 `crypto/rand.Read` 即可,再自行 base32/hex 编码,几行代码就能完成,没有封装的必要.

NewSecureId 是可排序、带时间前缀的安全 token,与纯随机 token 定位不同:前者天生泄露时间以换取排序和时间范围扫描,后者不含任何可推断信息.二者用途分开,不把纯随机需求塞进 NewSecureId.
